本期周报覆盖 2026 年 7 月 26 日至 8 月 2 日。

上一篇周报提出，要把已经完成的后端能力带到真实用户界面，并继续压实权限和文档边界。本周的开发基本沿着这条路线推进：积分系统补齐了工作台操作闭环，业务授权切换到 OpenFGA，成员角色和治理选民规则完成了一轮系统性整理，Workspace 首页也开始从“按模块陈列”转向“按成员当前事务组织”。

## 本周已完成的主要工作

### 1. 积分系统从 API 走进工作台

积分系统本周补齐了第一批面向真实使用者的页面和操作入口，包括：

- 成员创建、查看、取消和申诉兑换订单；
- 治理人员审核和履约兑换订单；
- 商户查看结算记录；
- 治理人员管理积分预算；
- 治理任务发布、预算锁定和任务验收发分；
- 用于人工验收的积分测试数据命令。

这意味着上一篇周报中“补齐积分系统 UI”的核心目标已经完成。积分发行、任务预算、任务奖励、兑换、销毁和商户结算不再只依赖 API 或命令行，可以通过 Workspace 按角色完成主要流程。

同时，相关产品说明、页面清单、世界数据库说明和 Workspace 页面文档也同步到了文档站。

### 2. 业务授权正式切换到 OpenFGA

本周引入 OpenFGA 作为统一授权系统，并使用官方 SDK 接入 Live OS。成员工作台、API、财务、模拟实验室和世界管理等入口逐步收束到统一授权服务，不再由各页面分散推导权限。

围绕这次切换，还完成了以下加固：

- 支持资源级授权关系投影；
- 提供授权模型初始化、关系重建和探测命令；
- 修正关系重建过程，避免留下旧授权关系；
- OpenFGA 不可用时采用失败关闭，并统一用户可见的错误提示；
- 启动脚本补充本地 OpenFGA 环境初始化和模型校验；
- 文档站同步本地开发、数据库、治理边界和迁移说明。

这轮改造的重点不只是更换权限组件，而是明确了一条架构边界：Django 保存权威业务事实，OpenFGA 根据这些事实回答“谁能对什么资源做什么”，页面和 API 只消费统一的授权结果。

### 3. 成员角色与治理权限模型完成重构

项目对角色、权限和身份展示做了一次系统整理。角色目录、角色分配、权限基线、身份展示和审计命令被拆分成更清晰的领域能力，并补充了专业领域与成员专业资格模型。

在此基础上，系统进一步统一了项目中的角色用语，引入“守约者”角色体系，并清理旧角色名称在模型、命令、模板、演示数据和测试中的残留。代码检查也增加了角色用语审计，降低以后再次出现同义角色和权限漂移的风险。

角色重构没有把“角色”与“权限”混成同一件事：角色是权威业务事实和公开身份，具体操作权限仍由授权策略决定。这为后续治理规则调整保留了空间。

### 4. 治理提案支持可配置选民规则

过去提案的选民范围更接近代码中的固定判断。本周新增了可配置选民规则，使提案能够按照确定的规则选择有投票资格的人群，并保存相应的规则快照和审计信息。

这项变化让“谁可以对某类提案投票”从隐含逻辑变成了可检查、可测试的治理配置。对应的数据库结构、OpenFGA 策略、示例 payload 和技术契约也已同步更新。

需要说明的是，可配置不等于可以随意修改。选民规则仍然要受治理流程、角色事实和权限边界约束，文档站记录的是当前系统能力，不替代正式治理决定。

### 5. Workspace 新增“我的事务”聚合视图

截至 8 月 2 日，Workspace 首页新增了“我的事务”区域，把任务、申诉、治理提案和采购事项按成员与事项的关系聚合为：

- 需要我处理；
- 等待他人处理；
- 最近结束。

成员现在可以先判断“什么与我有关、当前轮到谁、下一步能做什么”，再进入具体业务模块。开放但尚未领取的任务仍作为可参与事项展示，不会被误认为已经属于某个成员的个人事务。

这次改动只增加只读投影，没有新增通用事务表，也没有统一各领域的状态机。旧首页模块和操作入口仍然保留，便于迁移期对照、验证和回退。

### 6. 任务工时与开发环境继续收敛

任务标准工时改为使用整数分钟保存和传输，避免小时小数在页面、API、示例数据和模拟过程中产生含义差异。相关迁移、序列化、演示数据、技术契约和测试已经同步。

本地启动与迁移文档也做了整理：启动脚本会检查开发网络和 OpenFGA 初始化条件，文档进一步明确 MySQL、世界数据库、授权模型和管理命令之间的关系。

## 文档站本周进展

文档站本周主要承担了实现同步和术语收敛：

- 同步积分工作台、任务管理和积分预算页面说明；
- 更新 OpenFGA 架构、初始化、迁移和故障边界；
- 更新角色、权限、成员身份和治理边界文档；
- 新增角色与权限人工验收说明；
- 同步任务分钟字段和相关技术契约；
- 新增“大苹果社区”“守约者”“自由生活”等名词解释入口。

这批更新让产品说明、开发手册和机器可读契约能继续对应实际实现。文档站仍然坚持只发布准备长期维护的内容，OpenSpec 等实施过程材料继续留在 Live OS 仓库中，不混入公开产品文档。

## 本周的关键取舍

本周最重要的取舍，是没有为了“统一”而新增一个包办所有业务的通用模型。

OpenFGA 统一的是授权判断，不取代 Django 中的权威业务事实；“我的事务”统一的是成员视角下的只读投影，不取代任务、申诉、提案和采购各自的领域模型；角色目录统一的是身份语义，不把角色名称直接当作全部权限答案。

这种边界会让实现多一些映射和测试，但可以避免授权系统、页面聚合层或角色名称反过来成为新的业务真相来源。

## 下周预计工作

### 1. 验收新的成员事务首页

围绕真实成员路径检查“需要我处理、等待他人、最近结束”的归类、排序、权限隔离和跳转入口，并确认旧模块中哪些内容仍然必要。未经逐项确认，不直接删除迁移期保留模块。

### 2. 继续验证角色与选民规则迁移

使用角色审计、权限基线、OpenFGA 关系重建和治理流程测试，继续排查旧角色名称、历史数据和边界权限。重点验证不同角色在成员申请、提案、采购、申诉和财务流程中的真实可见范围。

### 3. 补充 Workspace 聚合视图文档

将“我的事务”的展示范围、只读投影边界、旧模块保留规则和人工验收步骤同步到公开文档，明确它是成员导航层，而不是新的权威业务模型。

### 4. 继续以真实操作路径做回归

把积分、任务、治理和采购的页面操作串联起来，优先验证成员和治理人员能否从 Workspace 完成完整流程，同时检查 OpenFGA 不可用、无权限和历史数据异常时是否安全失败。

## 本周结论

本周最大的进展，是 Live OS 开始形成一条更清晰的“成员操作—领域事实—统一授权—公开说明”链路。

积分系统已经从后端闭环进入工作台；OpenFGA 接管了跨模块授权判断；角色和选民规则从分散约定变成可审计结构；Workspace 首页则开始围绕成员当前要处理的事务组织信息。

下一阶段的重点，是用真实用户路径验证这些能力能否稳定协同，并让文档准确说明各层职责，避免把角色、授权、事务投影和权威业务状态混为一谈。
