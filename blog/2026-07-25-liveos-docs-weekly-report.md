这是大苹果项目的第一篇周报。本周开始，我们会用文档站持续记录 Live OS、社区规则、技术契约和产品路线的进展。

这篇周报先做一次阶段性回顾：从项目创立到 2026 年 7 月 25 日，Live OS 已经从一个社区操作系统原型，逐步形成了成员、治理、任务、公共审计、资源、财务、模拟和积分兑换等后端能力；文档站也从空白项目变成了可公开阅读的产品、架构和技术契约入口。

## Live OS 已完成的主要能力

### 1. 开源化基础与项目运行骨架

Live OS 已经完成面向开源协作的基础整理，包括项目结构、运行脚本、测试入口、管理命令和本地开发约定。当前后端以 Django 为核心，围绕“社区真实运转”建立模型，而不是只做展示型页面。

项目中已经有完整的测试体系和 smoke workflow，用来验证从成员、任务、事件到账本的关键路径是否仍然可用。

### 2. 成员、身份与加入流程

Live OS 已经实现成员账号、正式成员编号、成员资料、公开成员页面、凭证展示、成员申请和加入审核相关能力。

当前系统区分了普通账号、成员申请、正式成员和治理权限等概念，为后续社区准入、权限边界和公共展示打下了基础。

### 3. 治理、提案与投票

项目已经实现治理提案、成员准入投票、审批流和治理相关事件记录。社区不只是由管理员直接操作，而是逐步形成“有记录、有权限、有流程”的治理基础。

同时，采购挑战、审批、公共议题和后续治理规则调整，也已经有了可以继续扩展的模型入口。

### 4. 任务、贡献与工作台

Live OS 已经支持任务发布、领取、提交、验收和成员工作台展示。成员可以通过工作台看到与自己相关的任务和贡献记录。

本周积分系统接入后，任务验收不再只是生成普通记录，而是可以进入权威积分账本：任务奖励从预先锁定的预算发放，成员余额由交易流水推导。

### 5. 公共事件、观察者视图与审计链

项目已经实现公共事件记录、观察者事件浏览、哈希链校验和公开时间线。这个方向很重要：社区治理和资源分配不能只依赖后台数据库，还需要让成员能验证关键事实是否被公开记录。

目前公共审计链已经用于成员、治理、任务和积分相关事件。积分系统中特别注意了隐私边界：公开事件可以证明发生过积分交易，但不直接公开个人敏感交易金额和内部流水编号。

### 6. 模拟世界与社区推演

Live OS 已经具备 zero-start simulation、世界初始化、重置、模拟档案和推演相关能力。它的目标不是做游戏，而是在社区正式运行前，先用模拟方式检验规则、流程和资源压力。

这为后续测试“成员增长、任务供给、积分发行、兑换压力、财务负担”等复杂问题提供了基础。

### 7. 资源、库存、采购与财务基础

项目已经开始覆盖社区资源、库存维护、资源页面、采购流程、匿名捐赠、报销和财务公开等能力。

这些能力还没有全部变成完整业务闭环，但它们已经构成了 Live OS 的一个重要方向：社区不只是成员和任务，还包括物资、空间、现金、设备、库存和公共责任。

### 8. 积分、兑换与商户结算一期

本周完成了积分系统一期后端能力，这是 Live OS 的一个关键里程碑。

已经实现的核心能力包括：

- 单一积分体系：不拆成“贡献积分”和“消费积分”。
- 历史贡献和当前余额分开统计。
- `CreditAccount` 与 `CreditTransaction` 权威账本。
- 公共发行池、任务锁定账户、成员账户、冻结账户和销毁账户。
- 治理发行、任务预算锁定、任务验收发分、未用预算退回的服务层能力。
- 成员自由转账 API。
- 兑换订单 API：创建、冻结、取消、申诉、履约和销毁。
- 商户结算一期：区分成员微创业和现金结算商户。
- 现金结算商户收到的是人民币应收记录，不是可继续流通的积分账户余额。
- 幂等键、语义校验、并发保护、冲正入口和公开事件审计。

需要明确的是：积分系统当前主要完成的是模型、服务层、API、技术契约和测试。很多能力还没有对应的浏览器 UI，例如自由转账表单、兑换订单页面、商户结算列表和治理履约页面。这些会进入下周工作。

## 文档站已完成的主要能力

### 1. Docusaurus 文档站搭建

文档站已经完成基础搭建，支持中文和英文结构，具备首页、导航、产品文档、架构文档、开发文档和技术契约入口。

文档站的定位不是代码仓库的附属 README，而是大苹果项目的公开说明书：让成员、贡献者、技术参与者和未来社区运营者理解系统为什么这样设计。

### 2. 产品、架构和开发文档迁移

Live OS 中原本分散的说明内容已经逐步迁移到文档站，包括项目概览、路线图、数据库结构、API 说明、治理边界和开发协作规则。

这让 Live OS 代码仓库可以更专注于运行系统本身，文档站则负责解释产品语义、架构边界和公开协作方式。

### 3. Technical Contracts

技术契约已经迁移到文档站，并以机器可读文件形式发布。当前包括 API、schema、example 和相关校验脚本。

本周积分系统同步增加了自由转账、兑换订单、商户资料、商户结算记录等契约。后续会继续控制契约数量，只保留真正用于 API 或跨仓库协作的文件，避免把草稿也混入正式契约目录。

### 4. 文档治理与清理

本周也对文档站做了一轮结构清理：将不适合公开提交的草稿、阶段性设计和临时内容移出正式文档目录，避免文档站变成半成品堆积区。

后续原则是：正式文档写清楚“已经实现什么、尚未实现什么、下一步计划是什么”；仍在讨论中的内容先进入草稿区，成熟后再发布。

## 当前阶段判断

从项目创立到现在，Live OS 已经不再只是概念验证。它已经有一组可运行、可测试、可审计的核心业务能力：

- 成员加入与身份管理；
- 治理与投票；
- 任务与贡献记录；
- 公共事件与审计链；
- 资源、库存、采购和财务入口；
- 模拟世界；
- 积分发行、流转、兑换和商户结算一期。

但从真实用户使用角度看，当前仍然偏“后端和 API 先行”。下一个阶段的重点，不是继续堆更多模型，而是把已经完成的能力变成成员和治理人员能在浏览器中完成的实际操作。

## 下周预计工作

### 1. 补齐积分系统 UI

下周最重要的工作，是给已经完成的积分系统补上真实用户界面：

- 工作台展示当前可用积分和历史累计贡献；
- 成员自由转账页面；
- 兑换订单列表、创建、取消和申诉页面；
- 治理人员履约兑换订单的页面；
- 商户结算记录查看页面。

这些页面完成后，人工测试就可以以真实用户点击为主，而不是依赖命令行或直接调用 API。

### 2. 整理积分系统正式产品文档

积分系统的规则已经比较清楚，但正式文档还需要重新组织。下周应把它整理成三个层级：

- 已实现能力；
- 已确定但尚未实现的规则；
- 仍需治理讨论的开放问题。

这样可以避免把头脑风暴、临时设计和已经上线的 API 混在一起。

### 3. 建立人工验收清单

下周需要基于真实 UI 写一份人工验收清单，覆盖：

- 成员看到积分；
- 成员转账；
- 成员创建兑换；
- 成员取消或申诉；
- 治理人员履约；
- 商户查看结算；
- 权限隔离；
- 公开审计不泄露隐私。

这份清单应面向真实用户操作，不再把命令行脚本当作人工验收步骤。

### 4. 继续压实公开审计与隐私边界

积分系统必须能证明每一分从哪里来、经过哪里、最终在哪里销毁。但公开审计不能等于公开每个人的隐私明细。

下周会继续检查公开事件、成员页面、工作台和商户页面之间的边界，确保“总量可审计、个人隐私受保护”。

### 5. 文档站继续保持收敛

文档站下周要保持两个原则：

- 正式目录只放准备公开长期维护的内容；
- 草稿、实验、临时规划不要进入正式导航。

每周周报会成为一个固定节奏：记录已经完成的内容、遇到的取舍、下周准备做什么。

## 本周结论

本周最大的进展，是 Live OS 的积分系统从业务规则讨论进入了可运行后端：账本、预算、任务奖励、兑换、销毁、转账和商户结算已经形成第一版闭环。

下周的关键，不是再扩张概念，而是让这些能力真正出现在用户界面里，让成员、治理人员和商户都能按真实流程操作，并让文档站准确反映“系统现在到底能做什么”。
